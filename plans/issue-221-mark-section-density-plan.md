## Why extend file-hashes (and why MARK regex is appropriate here)

CLAUDE.md says: "Do not use regex grep for cataloging." That guidance is about **structural facts** (types, functions, generics) where regex misses generics / sees comments / can't compute shapes. MARK lines are *literally comments* in a fixed syntactic form (`// MARK: <title>` or `// MARK: - <title>`) — regex is the right tool for the matched-syntax case.

Reasons to keep this in file-hashes rather than spinning up a new extractor:

- file-hashes already walks every source file with package resolution + skip rules.
- Both `mark_count` and `line_count` are per-file scalars — exactly the shape file-hashes carries.
- A dedicated "marks-catalog" extractor would duplicate the walker logic for one field.
- Swift-specific via the extractor's existing `--extensions swift` pathway; the same regex would safely no-op on TS files (no `// MARK:` convention), but the query header documents Swift as the calibration target.

## Decision: defer Swift extractor MARK extraction to follow-up?

The task notes call this out: "mirror for Swift if `SwiftSyntax` exposes MARK trivia easily — if not, defer Swift's MARK extraction to a follow-up issue."

**Decision: keep MARK detection in file-hashes (Node-side regex), NOT in the Swift extractor.** Rationale:

1. MARK is a comment trivia node. SwiftSyntax exposes it via `.trailingTrivia` / `.leadingTrivia` walking, which is straightforward but requires wiring into the AST visitor pipeline. The marginal accuracy gain over a text regex is zero — `// MARK:` is not ambiguous, never elided, never inside a string in any real Swift file.
2. The file-hashes approach is language-agnostic. If TypeScript or another language adopts a `// MARK:`-like convention in future (it has not), the same query works without extractor changes.
3. Keeping the Swift extractor focused on type / function structural extraction matches the principle.

If real-world calibration shows the regex misses or over-fires (e.g., `// MARK:`-in-string-literal becomes common — it isn't today), a follow-up can move the detection into the Swift extractor's trivia walker. Documented in the query header as a known v1 limitation.

## Extractor: `--scan-marks`

```js
// Swift convention: `// MARK: <title>` (sometimes `// MARK: - <title>`).
// We intentionally accept both — the `-` separator is just visual.
const MARK_RE = /^[ \t]*\/\/\s*MARK:\s*-?\s*(.*?)\s*$/;
```

A new helper `scanMarks(buf)`:

1. Decode bytes as UTF-8, split on `\n` (after `\r\n` → `\n`).
2. `line_count = lines.length` (one of the two fields the query consumes).
3. For each line, test `MARK_RE`. On match, push `{ line: i+1, label: capture-group-1 }`.
4. Return `{ mark_count: matches.length, line_count, mark_labels: matches }`.

In `hashFile`, when `--scan-marks` is set, spread the result onto the record. The three fields are always present when the flag is set (`mark_count = 0`, `mark_labels = []` on files with no MARKs).

When `--scan-marks` is unset, the fields are omitted entirely.

## Query

Front-matter:

```jq
#! query: mark-section-density
#! shape: cluster
#! catalog: file-hashes
#! arg: min_marks number 6
#! arg: min_lines number 400
#! formats: text, jsonl
#! desc: Long files with many MARK: sections — maintainer-pre-labeled refactor candidates.
```

Thresholds are positional `--argjson` parameters (matching `near-duplicates` / `function-duplicates` convention), so callers can recalibrate without env-var ergonomics. Defaults `min_marks=6`, `min_lines=400` come from the issue body.

The query operates on file-hashes entries, filtering on `mark_count != null AND mark_count >= $min_marks AND line_count > $min_lines`. Each file produces one single-member cluster row.

Cluster_id format: `mark-section-density:<package>:<file>`. Single-member-per-row.

Member shape:

```jsonc
{
  "package": "...",
  "file": "...",
  "line_count": 812,
  "mark_count": 13,
  "mark_labels": [
    { "line": 12,  "label": "Singleton" },
    { "line": 67,  "label": "Player Factory" },
    { "line": 134, "label": "State" }
  ]
}
```

Sort order: `(-mark_count, -line_count, package, file)` — densest-first so report readers see the strongest signals at the top. (Note: `versioned-type-pairs` uses ascending sort by `(package, base_name)`; `function-duplicates` uses descending by member count. Density-by-count matches the function-duplicates precedent.)

### Text-mode render

```
[13 marks / 812 lines] cid=mark-section-density:app:iOS:Sources/.../AudioPlayerController.swift
    app:iOS:Sources/.../AudioPlayerController.swift
      L12   Singleton
      L67   Player Factory
      L134  State
      ...
```

The leading `[<n> marks / <m> lines]` annotation makes the density searchable in scrollback.

## Cluster_id

```
mark-section-density:<package>:<file>
```

`cluster_id_single_name("mark-section-density"; "\(.package):\(.file)")`.

**Uniqueness of `(package, file)` in file-hashes**: the extractor walks `--root` once (tagging `package: "main"` or per-package Swift mapping per `resolveSwiftPackage`) and `--shared` once (tagging `package: "shared"`). Each walk produces one row per source file, with `file` the path *relative to that root*. Two distinct walks producing the same `(package, file)` would require either (a) both `--root` and `--shared` resolving to the same on-disk path (single-walk degenerate case — same row appears once), or (b) a Swift path `Shared/X/...` colliding with a TS path under `--shared` — but Swift-mode and non-Swift-mode disambiguate by extension. The contract holds: `(package, file)` is unique within `file-hashes.json` by construction.

The same shape works for `copied-from-header` (PR #220) for the same reason. If a future schema bump weakens this guarantee, both queries would need to switch to `cluster_id_sorted_paths(prefix; ["\(.package):\(.file)"])` together — the migration is mechanical.
