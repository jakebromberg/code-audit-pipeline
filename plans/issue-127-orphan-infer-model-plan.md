# Issue #127 — orphan-InferModel query + `$inferSelect` extractor extension

Tracker child of #116, Phase 1. Ships a new cluster query that surfaces drizzle tables nothing in the catalog derives a TS type from, plus a ~5-line extractor extension so the modern `typeof X.$inferSelect` form is recognized in the same way as the legacy `InferSelectModel<typeof X>` form.

## Scope

One PR ships both pieces (issue's own recommendation, option b). The query branches on both legacy and modern API forms, so without the extension the query produces a measurable and growing false-positive rate — every codebase that has migrated to `$inferSelect` reports its derived tables as orphans. The extension is small enough (~5 lines + one doc bullet) that fanning it out into a separate PR adds more overhead than it saves.

## Cluster_id

`orphan-infer-model:<package>:<file>:<line>:<name>` via `cluster_id_single_name("orphan-infer-model"; loc_key(.))`. Drizzle table variable names are unique within a file but can collide across packages (e.g., `shared/users` and `main/users` re-export shimming) — the loc_key keeps each orphan row unambiguously addressable. The grouped-vs-pair `cluster_id` distinction in `_canonical.jq`'s header doesn't quite fit this query (one row per orphan, no grouping), so loc_key is the safer choice — same approach `function-duplicates-exact` took when names alone were insufficient.

## Open questions (issue body §"Open Questions" 1–5) — disposition

Per the issue's own "Defer questions 1–5 to a follow-up issue" recommendation, all five are out of scope for v1:

1. **Dangling InferModel** (inverse query, `infer_ref.table` doesn't resolve) — file as a separate issue if observed in real catalogs; v1 doesn't index it.
2. **Naming-pattern clustering** (`_archive`, `_legacy` suffix-stem) — premature; ship the raw list, see whether the cohort pattern actually emerges.
3. **Alias mismatches** (`InferSelectModel<typeof users as Users>`) — out of scope; AST work, not query work.
4. **Re-export aliases via barrel** — known limitation; document in query header.
5. **Generated tables** (`generated: true`) — exclude by default. Drizzle Kit output is rarely user-authored and orphan status there is noise. Add an `INCLUDE_GENERATED=true` env knob mirroring `migration-progress.jq`'s convention so the filter is opt-out.

The §5 decision (exclude generated by default) is the one design choice I'm locking in beyond the issue body — it's consistent with `migration-progress.jq` and prevents the most predictable noise source.

## Risks / known limitations to document inline

- **Re-exports through barrels**: a drizzle table declared in `shared` and re-exported as a different name in `main` won't be matched. Documented in the query's header docstring with the issue #4 open-question reference.
- **Alias-on-import** (`InferSelectModel<typeof foo as Bar>`): the extractor only sees the original identifier (`foo`), so derivations using `Bar` as the alias still match. The `infer_ref.table` value is `foo`, not `Bar`. Worth a one-liner in the header.
- **Identifier-only join**: the join is on `drizzle.name == infer_ref.table` (TS identifier), not on `db_table_name`. A renamed-in-SQL-but-not-in-TS table still matches; a renamed-in-TS-but-not-in-SQL table doesn't. This is correct for the orphan-detection question being asked.
